### 3.1 附件2对工程实现的新增要求

附件2要求技术报告呈现九个部分，因此实现阶段必须同步生成报告可用的事实和证据，不能在 10 月才回忆开发过程：

- 需求与方案：API、数据流和系统图必须与实际实现一致；
- AI 与开源选择：每个运行时资源暴露名称、锁定版本、来源、许可证/授权和用途；
- 设计与实现：保留架构版本、关键问题、解决记录和可公开的提交/变更证据；
- 成果展示：核心页面提供稳定演示数据和可复现操作路径；
- 效果验证：评测程序输出机器可读原始结果，图表不得手工录入数字；
- 创新与开放：实现可独立复用的规则库、检测器、测试或文档，而不是只交付 Web 外壳；
- 合规安全：实现许可证据、数据/隐私边界、提示注入/幻觉控制、免责声明和适用范围；
- 附录：资源清单和运行说明应由项目事实生成或半自动生成。

所有可见页面、报告模板和演示数据必须匿名，不显示学校名称、学校 LOGO、指导教师姓名、密钥或个人信息。

## 4. 文件所有权与协作规则

Terra 默认拥有：

Sol 默认拥有 `docs/` 架构/规范、`rules/schema/` 和 `benchmarks/specs/`。Luna 默认拥有批量 fixtures、资源台账、测试矩阵和文档初稿。由于当前项目不是 Git 仓库，三者共享工作目录：

- 开始修改前先查看目标文件是否属于自己；
- 不要在同一轮同时重写他人文件；
- 接口契约有歧义时在 `docs/coordination/change-requests.md` 记录；
- 需要 Sol 决策的变更不得先实现后通知；
- 每个功能合并前说明修改文件、运行命令、测试结果和已知限制。

## 5. 目标技术架构

### 5.1 前端

- React + TypeScript + Vite；
- ECharts 或 React Flow 展示资源关系；
- 以评委快速理解“发现了什么、证据在哪里、如何整改”为信息架构核心；
- 不追求过度动画，保证录屏稳定、字体清晰、在 1366×768 下可用。

### 5.2 后端

- Python 3.12、FastAPI、Pydantic；
- SQLite 作为比赛版持久化；
- 外部扫描器通过受限子进程调用；
- Jinja2 生成 HTML 报告，同时输出 JSON/CSV；
- 本地 Qwen3 通过 Ollama 执行非结构化抽取与解释；
- AI 不可用时提供确定性降级路径。

### 5.3 扫描工具

- ScanCode：文件许可证、版权、包信息；
- Syft：依赖与 SBOM；
- 自研 manifest 解析：Python 与 JS/TS；
- 自研 AI 资源检测：模型、数据集、API、Model Card、Dataset Card；
- SPDX 标准化；
- 自研风险规则引擎。

## 6. Terra 必须完成的工作包

### T0 - 工程底座

建立清晰的应用结构、配置系统、日志、错误处理和测试入口。建议后端包结构：

```text
backend/app/
├── api/
├── ingestion/
├── scanners/
├── domain/
├── knowledge/
├── risk/
├── ai/
├── reports/
├── persistence/
└── security/
```

要求：

- 配置使用环境变量和示例文件，不提交密钥；
- 所有外部工具版本可追踪；
- 统一结构化日志并脱敏；
- 提供健康检查和版本信息端点；
- 提供一条最小 smoke test 命令。

### T1 - 安全输入与扫描任务

实现：

- 公开 Git URL 的受限浅克隆；
- ZIP 上传、大小/文件数限制、解压前估算和路径穿越防护；
- 本地目录扫描；
- 文件清单、SHA-256 摘要和不可变扫描输入记录；
- 任务状态：queued/running/partial/succeeded/failed/cancelled；
- 阶段进度、超时、取消、清理和错误分类。

禁止：执行仓库脚本、运行构建、安装依赖、信任符号链接、使用 shell 字符串拼接调用扫描器。

验收：路径穿越、压缩炸弹、超大文件、超多文件、超时和中断均有自动测试；失败不会留下敏感上传内容。

### T2 - ScanCode、Syft 与 manifest 适配器

每个适配器应具有：

- 明确输入/输出 DTO；
- 工具版本记录；
- stdout/stderr 限制；
- 超时、部分结果和错误映射；
- 原始结果的受控缓存；
- 到统一 `Component`、`LicenseExpression`、`Evidence` 的转换；
- 固定样例回归测试。

manifest MVP：

- Python：`pyproject.toml`、`requirements*.txt`、常见 lockfile；
- JS/TS：`package.json`、npm/yarn/pnpm lockfile；
- 依赖来源、版本范围、开发/运行时范围和证据字段。

### T3 - AI 资源检测器

识别：

- Hugging Face、ModelScope 等模型/数据集 URL；
- `from_pretrained`、下载与缓存调用；
- README、配置和示例中的模型 ID/数据集 ID；
- OpenAI、Anthropic、Google 等 SDK 或端点；
- 环境变量示例中的第三方服务名称，但不得记录真实值；
- Model Card、Dataset Card、自定义许可证链接。

输出须保留路径、行号/字段、原始片段摘要、解析器和置信信息。正则、AST/配置解析和 AI 抽取必须分层，便于消融。

### T4 - 统一资源图谱和持久化

按 Sol 契约实现实体与关系：

- 项目包含组件和 AI 资源；
- 资源引用许可证表达式；
- 许可证产生候选义务；
- 证据支撑资源、许可证、风险与整改；
- 扫描运行记录输入摘要、工具/规则/模型版本和时间戳。

SQLite 需提供明确迁移入口；所有报告由同一规范化数据源生成，禁止前端、报告器各自推导一套风险逻辑。

### T5 - 许可证知识与风险引擎

读取 `rules/schema/` 的版本化规则，至少实现：

- 缺少许可证；
- 冲突许可证声明；
- 署名/许可证文本可能缺失；
- Apache-2.0 NOTICE 待核查；
- Copyleft 再分发义务待核查；
- AGPL 网络服务义务待核查；
- 模型或数据集许可证缺失；
- 自定义许可证未识别；
- 可访问但无明确再利用授权；
- 外部 API 服务条款未登记。

风险只输出 `pass`、`warning`、`review_required`、`unknown`。每条 finding 必须有 rule_id、rule_version、证据引用、触发条件、解释和建议；不得输出“合法/违法”的最终法律裁决。

### T6 - AI 辅助模块

实现 Qwen3 + Ollama 的可替换接口：

- 非结构化候选字段抽取；
- 规则结果的通俗解释；
- 基于证据生成整改步骤；
- 草拟资源清单和 NOTICE；
- 对未知条款生成需人工核查的问题。

质量控制：

- 强制 JSON Schema；
- 只允许引用输入中已有的 evidence_id；
- 重试次数有限；
- 超时/不可用/校验失败时降级；
- 记录模型名称、版本/摘要、提示模板版本和耗时；
- 不把 OpenAI 开发模型作为参赛产品默认运行时。

### T7 - 后端 API

建议端点：

- `POST /scans`；
- `GET /scans/{id}`；
- `POST /scans/{id}/cancel`；
- `GET /scans/{id}/components`；
- `GET /scans/{id}/assets`；
- `GET /scans/{id}/findings`；
- `PATCH /findings/{id}` 或人工确认接口；
- `GET /scans/{id}/reports/{format}`；
- `GET /benchmarks/runs`；
- `GET /health`、`GET /version`。

OpenAPI 示例必须可运行；错误响应结构统一；列表支持筛选和分页；扫描任务不能阻塞 Web 请求线程。

### T8 - 前端产品闭环

页面：

1. 新建扫描；
2. 扫描进度与错误；
3. 总览仪表盘；
4. 软件/模型/数据/API 资源图谱；
5. 风险详情、证据和许可证原文链接；
6. 第三方资源清单人工确认与导出；
7. 基准评测结果与错误案例；
8. 设置、隐私与免责声明。

关键交互：

- 从风险一键定位证据；
- 显示“工具发现/规则判断/AI 解释”的来源层级；
- 明确未知和需人工复核状态；
- AI 关闭或失败时界面仍可使用；
- 演示样例可在 3-5 分钟内完整跑通或可靠回放固定结果。

### T9 - 报告与资源清单

导出 HTML、JSON、CSV 和竞赛要求的资源清单。报告包含：

- 项目概览和扫描环境；
- 组件和 AI 资源；
- 许可证分布；
- 风险、证据、规则和整改；
- 人工确认状态；
- 工具、规则和模型版本；
- 免责声明；
- 第三方资源台账字段。

输出必须稳定排序、可复现、可匿名化，不包含密钥和完整敏感片段。

附件2要求最终《开源及第三方资源使用清单》至少能导出以下列：

1. 资源名称及类型；
2. 版本/来源；
3. 许可证/授权类型；
4. 使用/开放方式；
5. 关键义务/限制；
6. 团队自主修改或开发内容；
7. 合规状态。

内部模型可保留 `official_url`、`evidence_id`、`verified_by`、`verified_at` 等扩展字段。导出层必须将其映射到附件2参考表，不得遗漏“团队自主修改或开发内容”；合规状态使用枚举并支持“已核验/待核验/不适用”。

### T9A - 报告证据导出接口

为 Sol/Luna 提供稳定的材料事实出口，建议生成 `artifacts/report-evidence/` 或等价目录，其中包含：

- 构建与运行版本信息；
- 系统模块、API 和数据模型摘要；
- 扫描演示的去敏截图清单；
- 基准原始 JSON/CSV 和图表数据源；
- 失败样例、错误分析和未达目标；
- 第三方资源表；

- 部署步骤与 smoke test 结果；
- 当前功能清单和已知限制。

证据导出不负责写竞赛结论，只负责提供可核验事实。每份结果带生成时间、代码/规则版本和复现命令。

### T10 - 部署与可复现运行

Docker Compose 至少包含：

- `web`；
- `api`；
- `scanner`；
- 可选 `ollama`；

提供快速启动、离线/无 AI 模式、工具版本检查、资源需求、常见故障、清理方式和演示数据。陌生用户应可按 README 在一台普通电脑上启动。
