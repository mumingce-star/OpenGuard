# P2 慕明策最小后端交付清单

用途：用于完成 P2-01 统一候选与最小 DTO 冻结，并解除 xzb 进入 P2 前端阶段 2 的后端契约阻塞。此清单要求的是最小可联调输入，不要求一次完成全部 P2 后端。

## 一、统一可执行候选

- [ ] 提供后端完整 commit SHA，不使用短 SHA 或“最新版本”代替。
- [ ] 提供前端完整 commit SHA，并确认与后端候选兼容。
- [ ] 提供本次联调使用的分支、启动入口、端口、必要环境开关和数据根说明。
- [ ] 标明候选是否包含未提交代码、额外补丁或本机专用配置；如有，提供可复现来源。
- [ ] 明确 AI、公开 Git、外部材料获取等能力的启用/关闭状态，不允许隐式启用。
- [ ] 确认 GET 请求不会创建扫描、Assessment、材料、报告、任务或触发模型/外部获取。

验收证据：三方在同一组完整 SHA 上启动；xzb 能读取一个固定 Scan 和 Assessment；启动步骤可重复。

## 二、L1 用途建议读取契约

- [ ] 给出正式接口的精确方法、路径和路径/查询参数。
- [ ] 给出正式响应 DTO/Schema；字段名必须由后端冻结，前端不自行命名。
- [ ] 明确结果与 `scan_id`、`assessment_id`、Assessment `version` 的绑定关系。
- [ ] 明确结果自身的稳定身份、版本或不可变引用方式。
- [ ] 明确用途、适用对象、精确资源版本或 revision、适用范围、主要条件、初步判断分别由哪个返回字段表达。
- [ ] 明确 `unknown`、`pending`、证据不足、材料缺失、部分结果和成功的正式枚举及含义。
- [ ] 明确 Evidence/Material/Rule 等引用字段，以及引用对象不存在或错绑时的错误响应。
- [ ] 明确模型失败、服务关闭、输入不完整、结果尚未生成和结果过期的 HTTP 状态、`error.code`、`details`。
- [ ] 提供至少一份真实成功响应和一份真实缺口/限制响应，均绑定完整 ID，不使用缩写。

验收证据：相同 URL 刷新后读取同一结果；前端无需计算第二套结论；未知状态不会被解释为肯定许可或授权。

## 三、L2 回答与补充材料写入契约

- [ ] 给出结构化回答提交接口的精确方法、路径、请求 DTO 和响应 DTO。
- [ ] 给出本地 LICENSE/NOTICE 小文本材料的选择或提交接口；明确是否采用 multipart、JSON 或既有受限材料接口。
- [ ] 明确允许的材料类型、编码、大小、数量和拒绝规则；不扩展为通用文件平台。
- [ ] 明确回答/材料与资源 ID、精确 revision/version、Assessment、Evidence 的绑定字段。
- [ ] 明确 source hash、材料 identity、解析状态和采用状态的返回方式。
- [ ] 明确幂等键的创建与重试规则；网络失败时是否允许复用同一键重试。
- [ ] 明确 CAS/version 冲突规则、期望版本字段、409 错误结构和重新读取方式。
- [ ] 明确同步或异步语义；若异步，给出 Job 状态、轮询路径、失败和超时结构。
- [ ] 明确成功后返回的新 Assessment/结果 ID 与 version，以及旧版本的直接读取方式。
- [ ] 明确重复提交、错资源、错版本、孤立材料、服务关闭、解析失败、材料过大和不支持格式的错误响应。

验收证据：同一材料能稳定绑定同一对象/版本；错绑被服务端拒绝；失败不会覆盖旧结果；重试不会制造无法解释的重复正式结果。

## 四、增量重算和版本读取规则

- [ ] 明确回答或材料被采用后，服务端如何确定受影响项。
- [ ] 明确哪些项重新计算、哪些旧项直接复用；前端不自行判断影响范围。
- [ ] 明确新事实、新绑定关系和 AI 路由变化如何分别计数或表达，不能只给平均成功状态。
- [ ] 明确旧 Assessment/结果快照保持不可变，且可以通过直接 GET 继续读取。
- [ ] 明确当前结果和历史结果的排序、分页或直接读取规则。
- [ ] 如提供前后变化摘要，必须由服务端返回；前端不得生成第二套正式差异结论。

验收证据：提交一个有效补充材料后出现新 version；相关项变化，未受影响项复用；旧版本响应保持不变。

## 五、同版本 Report/摘要关联

- [ ] 明确 Report V2 是否直接包含本版本的 L1/L2/层级摘要。
- [ ] 如果暂不能进入 Report V2，提供明确标注的同版本 companion summary，不修改或覆盖 Formal Assessment。
- [ ] 明确 Report/summary 与 Assessment ID、version、facts hash、usage hash 及材料引用的绑定字段。
- [ ] 提供 JSON/HTML 或配套摘要的真实读取样例。
- [ ] 确认 GET/下载不隐式触发扫描、Assessment、模型或材料获取。

验收证据：页面、JSON/HTML 和当前 Assessment 指向同一版本；AI 建议不会进入或改写 Formal Conclusion。

## 六、交付回执格式

请一次性回传：

1. 后端/前端完整 SHA、分支和启动命令；
2. L1 接口 Schema 与成功/缺口响应；
3. L2 接口 Schema 与成功、409、输入错误响应；
4. 固定联调对象的完整 `scan_id`、`assessment_id`、version 及相关资源/Evidence ID；
5. 写入前后两个结果的完整 ID 和直接读取 URL；
6. 已知限制、关闭开关和仍未实现项；
7. 对应测试名称与实际通过数。

## 七、不接受的替代方式

- [ ] 不用聊天接口冒充结构化 L2 正式提交。
- [ ] 不用 Formal Assessment dimensions 冒充独立 L1 用途建议。
- [ ] 不用 Mock、静态 JSON 或发送机旧回执冒充本机真实 API。
- [ ] 不让前端根据标题、许可证名、provider、Logo 或文本关键词推断正式字段。
- [ ] 不以“接口稍后补充”要求前端先发明 DTO。
- [ ] 不通过关闭校验、改数据库或覆盖固定样本完成验收。

## 八、xzb 可开工判定

以下四项全部具备后，xzb 才进入阶段 2 正式产品接线：

- [ ] 同一候选的完整 SHA、启动入口和固定真实对象已确认；
- [ ] L1 GET 与 L2 写入契约、状态和错误语义已冻结；
- [ ] 成功、缺口、失败和冲突的真实响应样例已提供；
- [ ] 新结果/旧版本读取与同版本报告关联规则已明确。
