# P2 cz 真实样本与解析语义交付清单

用途：用于完成 P2-01 的真实材料正反例冻结，并为 P2-02 L1 建议和 P2-03 L2 补证提供可追溯数据基础。样本负责提供事实与解析语义，不能替代后端正式 API，也不能把人工补充冒充自动发现。

## 一、真实正例

- [ ] 选择一个不局限于 Pydantic、且当前规则和材料真实支持的精确版本软件组件。
- [ ] 提供完整资源身份、provider/source、精确 version/revision 和固定来源。
- [ ] 提供与该对象匹配的 LICENSE/NOTICE 原始材料或可合法引用的固定来源。
- [ ] 提供材料 hash、来源位置、获取方式和人工复核状态。
- [ ] 写清实际用途、适用对象、适用范围和主要条件。
- [ ] 建立可追溯链：`用途 → 对象/精确版本 → 材料 → 条款或已有规则 → 条件/建议`。
- [ ] 标明每个结论对应的 Evidence/Material/Rule 引用，不仅给自然语言总结。
- [ ] 标明哪些字段是扫描自动发现、解析器产生、人工补充或模型建议。

验收证据：后端可将该链绑定到固定 Scan/Assessment/Resource；前端可以只按引用展示，不需要猜测许可证或授权状态。

## 二、真实缺口或限制例

- [ ] 选择一个确实缺材料、适用范围不清、声明冲突或当前解析能力不覆盖的真实对象。
- [ ] 提供完整资源身份和精确 version/revision；不能只给名称。
- [ ] 明确缺少的是许可证正文、NOTICE、授权事实、适用对象、用途范围还是版本绑定。
- [ ] 明确应保留的正式状态，例如 `unknown`、`pending`、证据不足或部分结果。
- [ ] 明确哪些结论禁止出现，例如“已授权”“已履行”“已合规”。
- [ ] 提供现有 Evidence 与缺口之间的关系，不能把“没有找到”解释为“不存在”。
- [ ] 如果样本由人工补充，必须标注人工来源，不能标成自动 L1 成功。

验收证据：页面能够明确显示缺口/限制；系统不会因为名称、Logo、provider 或 metadata license 字段而升级授权或核验状态。

## 三、本地 LICENSE/NOTICE 小材料样本

- [ ] 提供固定对象和精确 version/revision。
- [ ] 提供一个小型 LICENSE 或 NOTICE 文本，不扩展为任意文件上传。
- [ ] 提供原始字节 hash、编码、文件名、来源和获取时间。
- [ ] 指定它应绑定的 Resource/Assessment/Evidence，不允许成为无版本的孤立材料。
- [ ] 给出解析前事实、解析后新增事实以及对应 Evidence。
- [ ] 说明该材料是否被正式采用；“已上传”不等于“已采用”。
- [ ] 说明采用后允许改变的事实或建议，以及绝对不能改变的 Formal Conclusion。

验收证据：材料被正式采用后只更新相关项并产生新版本；旧版本仍可读取且字节不变。

## 四、官方 npm 精确版本样本

- [ ] 使用现有 `npm_acquisition.py` 支持的官方精确 package/version 元数据路径。
- [ ] 固定 package 名、精确 version、请求 URL、响应时间和原始响应 hash。
- [ ] 保存真实成功响应及其解析结果；没有成功响应则明确标为网络/环境阻塞。
- [ ] 区分 metadata 中的 license 声明与 LICENSE 正文核验，前者不得自动替代后者。
- [ ] 明确哪些字段被采用为事实、哪些只能作为线索、哪些仍需人工复核。
- [ ] 不增加 PyPI/Hugging Face 等新 provider，不增加分布式缓存或安装目标包。

验收证据：存在真实官方成功响应时才能标记该路径通过；手工下载或缓存文本不能冒充在线成功。

## 五、错误绑定与失败样例

至少提供以下小型负向样例及期望错误：

- [ ] 正确材料绑定错误 resource ID；
- [ ] 正确材料绑定错误 version/revision；
- [ ] Evidence 或模型引用指向不存在对象；
- [ ] 相同回答/材料重复提交；
- [ ] 解析或外部获取超时；
- [ ] 包含提示词注入文本的材料；
- [ ] metadata license 声明试图升级 authorization；
- [ ] 训练用途证据试图复用于分发用途；
- [ ] 无版本或无对象绑定的孤立材料。

验收证据：错绑由服务端拒绝；失败保留旧结果；TEST_ONLY 或人工样本不会被展示为 Owner 级正式事实。

## 六、解析语义说明

- [ ] 提供当前解析器真正支持的字段清单和版本。
- [ ] 对每个字段说明来源位置、规范化规则、空值/冲突处理和 verification status。
- [ ] 明确 `pending`、`verified`、`unknown` 的产生条件，禁止把 pending 声明改成 verified。
- [ ] 明确材料存在、材料被解析、事实被采用、义务履行四个状态彼此独立。
- [ ] 明确许可证观察不等于授权，Task done 不等于义务已履行或项目合规。
- [ ] 对当前不支持的用途或材料保留 gap，不用模型回答补成确定事实。

## 七、建议交付目录与清单

每个样本建议至少包含：

1. `manifest`：样本 ID、对象、精确版本、数据等级和预期状态；
2. 原始材料或合法固定引用；
3. 原始材料 SHA256；
4. 解析后的事实及字段来源；
5. Evidence/Rule/Material 引用关系；
6. 期望 L1 结果或明确缺口；
7. L2 采用前后预期变化；
8. 负向测试与期望错误；
9. 人工复核人、复核状态和未解决限制；
10. 对应测试名称与实际结果。

## 八、交付回执格式

请一次性回传：

1. 正例和缺口例的完整标识与精确版本；
2. 每个材料的来源、SHA256 和数据等级；
3. 用途到条件/建议的完整引用链；
4. 自动发现、解析器输出、人工补充和模型建议的字段划分；
5. 本地材料采用前后预期变化；
6. 官方 npm 路径的成功原始记录，或精确网络阻塞；
7. 错绑、重复、超时、注入等负向样例结果；
8. 当前仍不支持的范围。

## 九、不接受的替代方式

- [ ] 不用资源名称、Logo、provider 或 source URL 推断许可证和授权。
- [ ] 不把 metadata license 声明当作 LICENSE 正文核验。
- [ ] 不把手工补充样本描述为完全自动发现。
- [ ] 不把没有找到材料解释为材料不存在或资源已删除。
- [ ] 不把 Task done、材料上传成功或解析成功解释为义务已履行。
- [ ] 不以 Mock、synthetic 或口头说明替代真实样本来源链。
- [ ] 不要求前端根据自由文本推断正式状态或关系。

## 十、xzb 可消费判定

以下条件全部满足后，样本才可作为阶段 2 前端联调输入：

- [ ] 正例和缺口例均有完整对象、版本、来源和 hash；
- [ ] 字段来源和 verification status 可区分；
- [ ] 引用链可由后端正式 ID 表达；
- [ ] 预期结果与禁止结论均已写清；
- [ ] 自动、人工和模型产出没有混用。
