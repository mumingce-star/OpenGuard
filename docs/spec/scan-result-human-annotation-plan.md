# OpenGuard 扫描结果人工标签详细方案

日期：2026-09-11。文档状态：建议设计，尚未实施或冻结接口。

## 1. 目标与适用范围

目标是对一次扫描中的资源识别、证据关联、许可信息、风险提示和整改建议逐项留下人工判断、依据和复核记录，形成可导出、可回溯的审查结果。先支持人工操作，再按需要实现网页录入。人工签收不是法律裁决，也不自动代表整改完成。

本方案默认采用以下范围，不依赖新建服务：

- 首批沿用12条真实候选，软件、模型、数据集、API各3条，两名真人独立填写。
- 原始扫描JSON和原始报告保持不变；人工记录单独保存，通过任务ID、快照哈希和对象ID关联。
- 业务复核以已扫描结果为入口；需要召回率时，另建覆盖明确范围的人工资源清单。
- 本轮仅生成方案，不代填真人答案、不修改产品、不启动或停止服务。

### 已核对的项目现状

当前工作分支为`codex/scan-reliability-integration`，基线`4c9e16b`。团队集成版采用本机已获取的`5611c00`核对，不宣称它是远端最新版本。

| 已有内容 | 可复用部分 | 不能直接视为已有功能 |
|---|---|---|
| Component、AIAsset、Evidence、LicenseExpression、RiskFinding、Remediation | 稳定对象ID、证据定位、风险与资源关联 | 不能据此推断人工审批已经实现 |
| 集成版资源、风险、证据页面 | 结果浏览、证据阅读、原始成员展开 | 真实API模式的处理状态选择器被禁用 |
| 集成版`benchmarks/real-resource-review.md` | 12条候选、固定原文、两阶段复核表 | 文件记录人工0/24份，不代表真人已签收 |
| 静态资源Bench与评测器 | 实际预测生成、精确标签集合TP/FP/FN | 尚不支持直接导入完整人工标注表并评价五个维度 |

现有真实复核表在当前主工作树没有；本机固定验收副本中存在。复制模板后填写，保留固定副本不变；正式记录不要只放在被忽略的`.tools/`里。本文路径均相对仓库根目录，固定验收副本不是新的正式源码入口。

## 2. 实施方式选择

| 方式 | 优点 | 限制 | 建议 |
|---|---|---|---|
| 离线表单＋独立记录文件 | 立即可做，适合12条试标，不依赖部署 | 汇总和一致性检查需要人工或后续脚本 | 第一阶段采用 |
| 现有Web增加人工标注与服务端保存 | 与证据并排查看、权限控制、多人复核、导出一致 | 要新增契约、持久化、接口与页面验收 | 第二阶段采用 |
| 接入独立标注平台 | 大规模任务分配较方便 | 新依赖、数据搬运与运维成本，领域证据仍需适配 | 当前不采用 |

推荐先完成一批离线记录来验证标签是否够用，再在团队集成源码上开发相同数据结构。不要为了首批12条先搭建复杂平台。

## 3. 标注单位与三个必须分开的状态

基本单位是“某次扫描快照中某个对象的一项判断”。一个资源可以有多个风险，一个风险可以有多条证据和多条建议；不能只给资源打一颗总分。

界面允许以资源为入口填写一张表，结构化导出时分别保存资源判断、每条证据引用的支持关系、每个风险和每条建议。来源文件本身真实，并不代表它支持所有引用它的结论。

### 三种状态

| 状态 | 回答的问题 | 示例 |
|---|---|---|
| 标注流程状态 | 这份人工判断走到哪一步了？ | 草稿、已提交、存在争议、已定稿 |
| 问题处理状态 | 被指出的问题处理到哪一步了？ | 未处理、处理中、声称已处理、需补证 |
| 复扫验证状态 | 新的证据是否证明修复有效？ | 未复扫、复扫通过、复扫未通过、无法比较 |

三者不能互相自动升级。人工认为某条提醒正确，不等于问题已修复；手工点“已处理”，也不等于复扫通过。

现有P0的`verification_status`、`FindingOutcome`和`ScanStatus`保持原语义。新增人工记录不能直接修改扫描对象的`pending`、`verified`或扫描终态。尤其不能把AI产生的原始pending建议直接改成verified，绕过其生产者约束。

## 4. 标签字典v0.1建议

以下机器值是拟定的标注协议，尚未加入现有Schema。页面显示中文，不要求标注员记英文代码。每个判断必须显式选择，不预选“正确”。

### 4.1 通用判断字段

资源识别、证据支持、许可证识别三个维度使用：

| 中文 | 值 | 使用条件 |
|---|---|---|
| 正确 | `correct` | 本次检查范围内，明确证据支持系统值 |
| 部分正确 | `partially_correct` | 对象存在，但名称、版本、范围等部分字段错误；必须逐项指出 |
| 错误 | `incorrect` | 明确证据反驳系统判断或关联对象不符 |
| 无法确定 | `uncertain` | 已检查，但信息不足、来源冲突或无法定位 |
| 不适用 | `not_applicable` | 本对象没有该项评价对象，例如不存在AI建议；必须说明原因 |

尚未检查的字段存为`null`并留在草稿中。`null`与`uncertain`不同：前者没做，后者已做但无法判定。提交时，适用维度不得为null。

### 4.2 资源事实字段

| 字段 | 建议值或要求 |
|---|---|
| 资源类别 | software、model、dataset、api、other、uncertain |
| 名称 | 原文完整名称；保留provider/namespace；不只凭显示名匹配 |
| 版本状态 | exact、range、unfixed、uncertain；另存原文值 |
| 使用情境 | declaration、lock_record、source_call、example、documentation_reference、comment_reference、type_import、uncertain；允许多选 |
| 关系说明 | 一句话说明“谁在何处如何引用该资源” |
| 实际执行事实 | 只有运行证据才能声明已执行；源码出现调用表达式不证明调用已经发生 |

软件内部再记ecosystem；模型和数据集保留完整仓库标识；SDK依赖和API引用属于不同对象。记录同名多版本时使用对象ID和版本，不能只按名称合并。

### 4.3 证据与许可

证据性质允许多选：`resource_reference`资源引用、`license_declaration`许可声明、`authorization_record`授权记录、`uncertain`无法判断。它们不是证据强度的自动等级。

每条支持关系保存：被评价对象/具体主张、扫描Evidence ID或人工补充证据ID、locator、可用时的文件SHA-256、判断、理由。多个证据支持不同字段时分开记录。

许可信息额外保存：

- 系统原始表达式与人工建议表达式，分别保存；未确定时建议值为null并给原因。
- 来源对象、版本、文件/官方URL、定位、获取日期。
- 对应使用场景：本地试用、托管调用、修改、再分发等；不知道就写不知道。
- 该来源是否在原始扫描输入内：`scan_input`或`external_supplement`。

只看到引用或依赖声明，不能自动得到资源授权结论；根项目的许可证不自动转移给依赖、模型、数据集或API。访问申请获批与某种具体使用方式获准也要分开核验。此处不预设任何具体资源的许可答案。

### 4.4 风险标签

| 中文 | 值 | 条件 |
|---|---|---|
| 接受 | `accept` | 当前证据下，风险提示适用且措辞恰当 |
| 需修改 | `revise` | 提醒有合理部分，但结论、场景或措辞需要修订 |
| 拒绝 | `reject` | 证据与适用条件明确不支持该提示 |
| 无法确定 | `uncertain` | 尚缺适用场景或证据 |
| 不适用 | `not_applicable` | 无风险对象可评价 |

另存`proposed_outcome`，可用现有pass/warning/review_required/unknown，默认null；`proposed_severity`可用info/low/medium/high，默认null。这两项只是人工建议，不覆盖原始RiskFinding。接受一条“证据不足、需要复核”的提示，并不等于确认发生了违规。

### 4.5 AI或规则整改建议标签

主标签：`actionable`可执行、`too_generic`过于笼统、`incorrect`错误、`uncertain`无法判断、`not_applicable`无此对象。

附加问题码可多选：`unsupported_claim`无依据主张、`wrong_evidence`证据不相关、`wrong_order`步骤顺序不合理、`missing_prerequisite`缺少前置条件、`wrong_scope`适用范围不符。

可执行的判据：对象明确、核验入口可找到、动作可完成、预期留存结果明确，并且不依赖未经证明的前提。生成者是AI还是规则由原始producer读取，不由标注员随意重填。

### 4.6 错误原因与整改标签

统一错误码：wrong_type、wrong_name、wrong_version、duplicate、wrong_locator、irrelevant_evidence、unsupported_license、wrong_context、unsupported_risk、suggestion_problem、other。选择other时必须写解释。

处理进度使用open、in_progress、claimed_resolved、needs_evidence；复扫使用not_run、passed、failed、not_comparable。复扫passed必须关联新的scan_id、固定输入和受影响项目的比较记录，不能依赖人工按钮单独产生。

`blocking`表示是否阻止本条/本批签收，必须写明范围与原因。未知许可本身不必然阻断全部扫描；证据串错、伪造证据、无依据授权结论或报告无法使用，按现有复核规范阻断相应签收直至处理。

## 5. 真人操作SOP

### 第0步：建立标注批次

由协调人登记batch_id、目的、源项目固定commit或ZIP哈希、扫描任务ID、原始JSON附件SHA-256、OpenGuard版本、扫描/规则/AI配置、抽样规则、纳入与排除范围。

区分两种批次目的：`output_review`扫描结果复核，允许后续看系统结果；`benchmark_gold`评测真值，初始标注不展示系统输出。12条已有候选的名称和类别已经暴露，属于候选复核，不能追称盲测。

原始报告标记partial时保留partial。可以复核已有有效对象，但批次必须注明未覆盖阶段，不将局部签收写成整次扫描成功。

### 第1步：复制模板并分配角色

两位真人使用不同匿名角色ID，各自拿到12条原文入口。先填写日期、是否看过系统结果/对方答案。角色别名不应被描述成已认证身份；离线可追溯性依赖真实的个人提交记录。

建议正式目录（实施时创建，本文不生成答案文件）：

```text
benchmarks/annotations/<batch_id>/
  manifest.json               批次元数据与原始报告哈希
  reviewer-a.jsonl             A的独立记录
  reviewer-b.jsonl             B的独立记录
  resolutions.jsonl            裁决与修订记录
  summary.md                  范围、数量、分歧、阻断与限制
```

受限证据原件保存在经批准的本地位置，不默认进入Git。仓库可保存脱敏标注、允许公开的定位和哈希。原始报告含敏感内容时另生成脱敏导出，保留原件与导出件各自的哈希，不能假装两者字节相同。

### 第2步：先看原文事实

每条阅读定位上下文、依赖字段或锁文件记录，必要时读完整函数或文档段落。记录资源名称、版本、使用情境、证据性质与不确定事项。不执行被扫描项目代码，也不安装其依赖。

固定URL打不开时登记原因；不能悄悄改用main分支原文作为同一证据。新增外部来源单独登记版本和日期。

第一阶段答案保存并提交后锁定原版本。Markdown源码可能直接显示details内系统结果，独立判断时使用仅原文的视图或渲染预览，并如实披露既有接触情况。

### 第3步：逐项对照扫描结果

展开系统资源和风险，按资源识别→证据支持→许可信息→风险措辞→整改建议顺序填写。每项确认当前对象ID与版本；同类风险分组只是导航，不能直接把一条结论批量套到全部成员。

错误/部分正确/拒绝/需修改必须写错误字段、原值、建议值和依据。无法确定必须写缺少的信息。正确/接受也至少引用一处支持依据。AI无输出时选不适用，不计为建议正确。

### 第4步：提交独立记录

检查必填项、来源定位和对象关联后提交。两人均提交前不互看第二阶段结论。只有一名真人时记录single_review，不伪装成双人复核；此批不得满足双人门禁。

### 第5步：分歧处理

按同一对象、同一维度对齐A/B原始记录。名称、版本、证据或结论不一致时保留双方原话，追加裁决记录，包含争议字段、追加依据、最终判断和裁决人。

两人有充分依据可共同确认修订；仍存在关键分歧时由未参与初标的第三位真人裁决。没有第三人或证据仍不足时保留disputed/uncertain，不能让AI替代独立真人签收。

### 第6步：冻结与导出

冻结意味着批次成员、记录版本和裁决版本确定，不意味着所有对象都“通过”。导出分别列出已确认、无法确定、有争议、阻断项和排除项。

保留原始结果、两份独立判断、裁决和批次摘要。修订采用新版本和supersedes引用，不抹掉旧答案。

### 第7步：缺陷回流与复扫

缺陷报告至少包含扫描版本、输入版本、对象ID、复现位置、原输出、人工依据、期望行为。修复后生成新扫描，再比较受影响对象。

资源ID可能变化，不能按名称或旧ID自动确认新结果。使用类型、生态/provider、完整名称、版本、locator、内容哈希等做候选映射，由真人确认；内容/规则/模型/快照变化则旧标签不自动继承为已定稿。

## 6. 建议的网页交互

此节为待开发能力；当前集成版真实API模式只读。

### 入口与布局

- 扫描详情增加“人工标注”入口；显示原始扫描终态、批次范围、标注进度和未解决争议。
- 左侧对象列表：资源类别、名称/版本、关联风险数、本人标注状态；支持按错误、无法确定、阻断和未标注筛选。
- 中部证据阅读：路径/字段、行号、片段、固定来源、哈希状态；缺失定位明确提示。
- 右侧标签表单：五个评价维度、理由、建议更正值、补充证据。
- 原始机器值与人工建议并排展示，标明生成者和时间，不在原值上静默覆盖。

### 操作约束

- 提供“保存草稿”“提交本条”“上一条/下一条”，保存成功与失败有明确反馈。
- 关闭页面或切换对象时提示未保存修改；失败重试不得重复创建提交。
- 批量操作只用于分配人员或调整草稿任务状态；首版不支持批量确认许可、风险或建议正确。
- 第一阶段服务端响应不提供系统判断；双方未提交时不向另一人返回已提交答案。仅靠CSS隐藏不足以形成独立复核。
- 基准真值模式应隐藏机器候选；业务复核模式可以展示但记录exposure，不能混用统计。
- 提交后修订保留历史；裁决人可看双方记录和证据。导出与屏幕读取同一个冻结批次版本。

页面示例仅用于布局，不是真实标注：

```text
批次：一次固定扫描     原始终态：partial     本人提交：x/12
对象列表 | 原文与定位              | 人工标签
资源A    | 文件、字段、片段、哈希  | 识别：[请选择]
资源B    | 机器原始值（第二阶段）  | 证据：[请选择]
……       | 人工补充来源            | 风险：[请选择]
         |                         | 理由、更正值、保存/提交
```

## 7. 数据与契约设计建议

新增独立的Annotation协议，不创建第二套Component、Evidence或RiskFinding公共模型，不向冻结P0对象随意加字段。

### 7.1 批次与记录

| 对象 | 最少字段 |
|---|---|
| AnnotationBatch | id、schema_version、label_set_version、purpose、scan_id、scan_result_sha256、source_revision/input_digest、tool/rule/model版本、scope、sampling_method、created_at、status |
| AnnotationRecord | id、batch_id、reviewer_id、phase、target_kind、target_id、dimension、judgment、reason、evidence_refs、proposed_value、exposure、revision、supersedes、submitted_at |
| SupplementaryEvidence | id、source_scope、locator、source_revision、observed_at、hash及缺失原因、excerpt或受限引用、added_by |
| Resolution | id、batch_id、目标对象/维度、双方记录ID、最终标签、理由、补充证据、resolved_by、resolved_at、revision |
| RescanCheck | id、原批次/缺陷ID、新scan_id、新快照哈希、对象映射、验证状态、依据、操作者与时间 |

target_kind使用component、ai_asset、evidence、license_expression、finding、remediation；维度与目标类型绑定校验。证据支持关系额外指定所支持的主张/对象，不能仅凭Evidence自身“正确”传播给全部风险。

人工补充“漏检资源”使用独立的新增候选ID和定位，不能伪造原扫描对象ID。只有完整gold构建与匹配阶段才把它算作FN，部分浏览中发现的漏项先记缺陷数量。

proposed_value按维度定义允许字段，不接受任意JSON去修改业务对象。名称、版本、类别更正与许可表达式更正分开校验。

### 7.2 状态机

个人记录：draft → submitted；已提交内容不可原地改写，修订创建新revision并关联旧记录。

批次：draft → labeling → reviewing → finalized；存在未解决关键分歧时进入disputed，补证裁决后回reviewing。finalized为不可变快照；重新开启创建下一版，不修改已导出批次。

原始scan_result_sha256变化时，旧记录仍绑定旧快照；对新快照显示needs_revalidation，不能自动算入已复核数量。

### 7.3 保存、并发与身份

离线首版使用独立文件；Web版复用项目部署中的持久化方式，新增标注表、记录修订表、证据和裁决表，采用迁移管理。数据库文件保留在持久卷，不放容器临时层；最终集成测试在项目要求的Linux环境进行。

唯一约束覆盖批次、操作者、阶段、目标对象、维度和revision。提交带预期revision和幂等键；过期写入返回冲突，不最后写入者覆盖前者。提交记录、审计事件和状态更新使用事务。

服务端从可信会话确定reviewer身份，不信任请求体随意声明的角色。项目当前没有经本轮验证的多用户标注认证；首版若只有本地单用户会话，应明确展示身份仅为自报，不能宣称具有独立身份保障。真正双人在线独立复核需补齐会话和权限边界。

## 8. 首批样本与扩展策略

### 首批12条

沿用已有候选表，每类3条，两名真人各12份。目的为跑通标注流程、发现证据和措辞问题。类别/名称已经可见，不能宣称完全盲评；全来自检出结果，不能计算召回率。

开始正式标注前用另外的练习样例校准标签。正式12条不要先集体讨论答案。候选表已展示的系统内容如被看过，应披露。

### 第二批建议

在首批标签稳定后选3～5个固定项目，分别覆盖Python依赖、JS依赖、模型引用、数据集引用、API引用及容易混淆的注释/示例。数量是启动建议，不是统计充分性的保证。

建立两个分开的子集：

- 工程错误分析集：有意纳入未知许可、同名版本、错误定位、失败/partial、复杂表达式等困难案例，支持找缺陷。
- 效果评测集：预先定义总体、项目抽样、目录范围及完整标注规则，避免只挑系统擅长的候选。

同一仓库不同版本、同源fork或重复片段按项目族划分，不能随机按行分进开发与测试两侧。最终测试集冻结后不反复用于调规则；若已用于调试，标记为开发集并补独立测试集。

## 9. 统计口径

### 候选复核批次可以报告

- 标注进度：已提交记录数/应提交记录数；12条、两人时分母24。另列独立对象数12，不能把24次判断当成24个独立样本。
- 定稿进度：已完成裁决/一致性确认的对象数/纳入对象数；无法确定可形成定稿结论，但不得算“正确”。
- 各维度正确、部分正确、错误、不确定、不适用数量，附可评价分母。
- 初始一致率：双方原始标签完全一致的可比较对象-维度数/双方均完成且该维度适用的对象-维度数；不确定作为独立标签，不适用另报。
- 人工修正率：定稿后至少有一个机器字段需要改动的对象数/已定稿且可评价的被扫描对象数。只补充外部证据与修正机器错误分别计数；分母为0时报告不适用。
- 人工耗时：明确是实际操作计时还是自报时长；分别报告初标、复核和裁决，不混入模型或扫描耗时。

可执行建议比例仅对确实存在且完成评价的建议计算；同时公布不确定数量及分母。首批样本很小，优先公开原始计数，不给总体效果保证。

### 完整资源真值集才可计算

TP为匹配到的真实资源；FP为不符合预先定义资源范围的检出；FN为在完整标注范围内存在但未检出的资源。Precision=TP/(TP+FP)，Recall=TP/(TP+FN)，F1=2PR/(P+R)。

必须先冻结匹配规则：类别、生态/provider、完整名称和版本；版本范围与精确版本分开评分；同一case中的重复出现按已约定资源粒度去重，证据定位另行评分。不确定gold单列，不悄悄当负例或漏报。

现有评测器在零分母时返回0，应在评测说明保留此行为；业务复核比例的零分母显示不适用，二者不得混淆。负样例即使没有TP也应报告FP=0，不说“该样例准确率0”。

扫描失败率、partial比例、各阶段覆盖率单独报告。只有事先约定的技术评测才能把失败任务按空预测纳入端到端指标，并同时给出可成功扫描子集的结果；不能事后删掉失败任务提高指标。
